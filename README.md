# toolrx — tool calling without an LLM

`toolrx` is a deterministic micro tool-router and local harness. Give it a
plain-English request and it selects one of 27 allow-listed tools, extracts the
arguments, checks them against a default-deny policy, and executes — with no
transformer, no GPU, no API key, and no third-party Python packages.

```bash
TOOLRX_SANDBOX_ROOT="$PWD" PORT=8080 python3 toolrx/server.py
# open http://localhost:8080/  — then ask: "list contents of all files"
```

The dashboard shows the machine it is running on automatically: hostname, CPU,
RAM, load, uptime and disk are read from `/proc`. No device config is required.

## How it works

1. `tokhash.py` turns the request into hashed character n-grams (pure Python).
2. `builder.py` derives one centroid vector per tool from `knowledge/*.md`.
3. `router.py` scores the request against every centroid by cosine similarity
   and picks the best tool plus a confidence/margin.
4. `executor.py` extracts arguments, validates them with `security.py`, and runs
   the tool inside a realpath sandbox with bounded output size.

The model is `micro_model.json`: text statistics, not neural weights. Rebuild it
at any time with:

```bash
python3 toolrx/server.py --rebuild
```

## Quick start

```bash
# deterministic router + dashboard (no adb, no phones, no models)
TOOLRX_SANDBOX_ROOT=/path/to/some/dir PORT=8080 python3 toolrx/server.py

# call it from the shell
curl -s localhost:8080/call \
  -H 'Content-Type: application/json' \
  -d '{"query":"list contents of all files"}'

# run the routing tests
python3 toolrx/tester.py
python3 -m unittest discover -s tests -v   # routing + repo hygiene
```

GitHub Pages is not a screenshot: `docs/` ships the dashboard together with the
same `micro_model.json` and a JavaScript port of `tokhash.py` / `router.py`
(`toolrx/web/`). On a static host the router runs in the tab — 27 tools, real
confidence scores, a virtual workspace that persists in `localStorage`, and no
network calls. The Python server is only needed for machine/socket tools,
training, and WireGuard.

The tab also carries a deterministic command library generated by
`toolrx/build_commands.py` (`toolrx/web/commands.json`, 11,875 patterns:
arithmetic, unit conversions, text transforms, encoding, dates, colour, JSON/
CSV, generators, builds, projects, chat, and web lookups). A prompt is split on
`then`, `;`, `->`, or numbered lines, and each step can feed the previous
result. Build requests (`build an rpg`, `build a social media website`) render
a complete offline page from `toolrx/web/templates.js` into the preview pane
**and write a real mini-project** (`index.html`, `styles.css`, `app.js`,
`README.md`, `ARCHITECTURE.md`) into the active project under
`projects/<slug>/`. The ◫ button in the composer opens the project manager:
create, open, preview, or delete projects; the workspace and project files
persist in `localStorage`. Every project also has an `export` button that writes
a portable JSON document, and `⇩ Import project JSON` restores one without
overwriting anything (the import gets a unique slug).

Build modifiers are deterministic: `build a tetris game with 3d elements`
renders depth-sorted 3D cuboids with a small software projection renderer, and
`build an rpg based on king arthur` or `build an rpg based on india` produces
different themed worlds (Camelot, Bharata, Derelict, Rain City, Neon, Olympus,
Sakura, Nile, Abyss, Frontier, Frostfall, Cinderforge, Mycelia, Aether Reach,
Clockwork, Reverie, Blightfall, Tidewreck, Verdant Wood, Astral). Project
references are tolerant:
`change the name from verdant wood rpg to india`, `rename it to camelot`,
and `change the project name to bharata` re-theme the same project instead of
starting a chat or creating a duplicate.

Build modifiers are deterministic and are parsed into a one-line **build spec**
before any code is generated:

```
> build a top-down shooter with pixel art, 3 levels
spec · 2D top-down · shooter · pixel · 3 levels · seed 1233879146
```

The spec records dimension (`2D`/`3D`), view (`side-scroller`, `top-down`,
`isometric`, `first-person`, `third-person`), genre, art direction (`pixel`,
`low-poly`, `neon`, `monochrome`, `flat`, `vector`), theme, scale, and a seed.
The seed is a hash of the normalized prompt unless you write `seed 42`, so the
same request always produces the same files and an explicit seed replays a world
exactly. The one exception is a default RPG request: each build advances a
session counter before hashing, so consecutive `build an rpg` prompts land in
different packs. The printed `seed N` replays any one of them exactly.
Ambiguous requests still build the closest supported starter and say so:
`build a bullet hell` reports `closest supported: shooter`.

The step-18 game library ships ten 2D starters (platformer, top-down shooter,
twin-stick, roguelike, tower defense, top-down racing, merge/match puzzle,
farming sim, card battler, rhythm) and six 3D starters (first-person maze,
third-person platformer, kart racer, low-poly exploration, wave shooter, block
builder). Each one writes the same project skeleton and an `ARCHITECTURE.md`
covering state, entities, systems, balance knobs, and extension points;
`plan a <genre>` prints that brief and `build a <genre>` writes the working
offline starter.

The shared `engine2d.js` runtime powers the 2D builds (and the older arcade
templates). It provides a fixed-step loop, keyboard/pointer/touch input, camera
follow, tile and sprite drawing, AABB physics, particles, and WebAudio beeps.
Generated projects include it as a real file next to `app.js`; the preview
inlines the same source so it stays self-contained. `engine3d.js` adds a WebGL1
batch renderer with a Canvas2D perspective fallback for the 3D builds.

RPG builds ship two more real files: `worldgen.js` (seeded biomes, rivers, roads,
3–5 towns with houses, a multi-room dungeon, NPCs, enemies, pickups, and 4–5
quests) and `rpg2.js` (isometric explorer with camera follow, fogged minimap,
dialogue, shops, action combat, XP/levels, quest log, and three save slots).
Small worlds are 64×64 and `large` / `huge` requests reach 96×96. Sprites stay
procedural; the optional sprite-pack pipeline (step 14) is still blocked on a
licence-compatible atlas and is not shipped yet.

`build an rpg` picks its starting pack from the seed (twenty packs, from
Camelot, Bharata, Derelict, Neon, Rain City, Olympus, Sakura, Nile, Abyss, and
Frontier through Frostfall, Cinderforge, Mycelia, Aether Reach, Clockwork,
Reverie, Blightfall, Tidewreck, Verdant Wood, and Astral) instead of always
starting in Verdant Wood. The second ten default packs get generated
`<adjective> <place> RPG` titles, while named settings keep their curated
titles. Add `seed N` to replay a specific world.

Every result in the chat shows measured throughput as `tok/s` (estimated output
tokens = characters ÷ 4 over wall-clock time, with the step's token count and
milliseconds). It is a real measurement of the deterministic step, not model
inference, and the generated files are unchanged. The roadmap for build specs,
shared 2D/3D engines, a larger RPG world, sprite packs, and an optional LLM
adapter lives in `toolrx/vision/HARNESS-ROADMAP.md`. Steps 26–27 now accept a
2,000-character single route and plans up to 8,000 characters or 40 steps,
preview the ordered plan before running it, and stop at the first failed step.

build phrasing and duplicate detection. Step 29 expanded the build spec to
features, counts, levels, sub-themes, and explicit world sizes: long requests
now write a seeded `content.js` alongside `app.js`, and the RPG world honours
requested town, enemy, NPC, and quest counts. Step 30 adds additive
`grow project` / `expand module` / `add <system>` commands, atomic two-to-five
patch bundles, and configurable 16-deep undo. Step 31 adds a bounded,
per-project context store: `what is in context` prints the last result, the
last plan, the active spec, per-file summaries and hashes, and a rolling
session list, with a visible cap and eviction notes. `continue from previous`
runs only pending steps, `expand the last plan with …` appends steps without
running them, and `apply the same changes to the other files` replays the last
edit on every other project atomically. Context stays in `localStorage`, is
serialized with sorted keys, and never enters a network payload; its 35
routes bring the catalog to 12,502. Step 32 raises project files to 128 KB and
projects to 512 KB across at most 32 files, and makes long builds observable:
phase and per-file progress events carry a partial file list, and the final
event reports characters, estimated tokens, milliseconds, and peak bytes. A
build that would exceed the budget is refused before writing, and cancelling or
timing out leaves the previous project byte-for-byte intact. Step 33 captures
verbatim content: `write the following into notes.md:` copies everything up to
the end of input (or an `end`/`EOF` line) without lowercasing, plan splitting,
or truncation, refuses blocks over 8,000 bytes, and still rejects traversal,
absolute paths, NUL bytes, and injection patterns. Fenced and triple-quoted
arguments survive byte-exact, and `extract headings`, `outline`, `first N
lines`, and `table from …` turn a file or the previous step into deterministic
output. The next batch hardens those envelope numbers.

Step 34 expands all 27 knowledge documents with longer phrasings and targeted
disambiguation, without adding a second centroid layer: 109/109 measured routes
land correctly with a minimum margin of 0.019 and a median of 0.126, while the
rebuilt model stays at 469 KB (1.30× the 352 KB baseline) and rebuilds in about
1.3 s. Step 35 pins that envelope in tests: 27 long routing prompts (500–2,000+

`last run` chip above the preview; `toolrxWeb.lastRun()` exposes it and a reset

Step 36 puts a clock on every plan. Each step has a 4,000 ms wall-clock cap
(`toolrx.step.timeout`, 250–30,000 ms) and the whole plan has a 160,000 ms cap
(`toolrx.plan.timeout`, 250–600,000 ms), alongside the existing file, project,
and build budgets. The plan preview reports the active chars, steps, per-step
time, plan time, worst-case time, and whether the request fits; a plan whose
worst case exceeds the wall budget is refused before any step runs with the
limiting cap named. A step that overruns reports `budget.timeout` and stops the
plan without writing. The final run report now carries headroom for files,
bytes, steps, characters, and time, and the dashboard `last run` chip shows the
remaining room while its tooltip shows used/max for each cap. Python plans
report the same envelope and stop on the same conditions.

Step 37 makes the fixture file the source of truth for the long-form envelope.

Step 38 removes the last private copies of the numeric envelope.
`toolrx/limits.json` is the checked-in source of truth for single-route and plan

Step 39 makes context inspection and continuation honest under pressure.
`context snapshot` stores a deterministic per-project shape of the context
(sorted kind/key entries with byte counts and hashes, stored bytes and sha,
pending plan steps, and eviction notes) without adding an entry or touching the
network. `diff against previous context` prints added, removed, and changed
entries in that same order, the entry and stored byte deltas, and the pending
step delta. A dedicated plan marker survives the general eviction ring, so
`continue from previous` and `expand the last plan with …` say exactly whether
the stored plan was trimmed or evicted and ask for a rebuild instead of
pretending there is nothing there. A pending plan also survives a project
switch with no duplicate steps.

Step 40 turns project growth into a real system library. Eleven seeded systems
(`inventory`, `dialogue`, `combat`, `save`, `quests`, `crafting`, `ui`,
`audio`, `weather`, `particles`, `ai`) each write a named file under
`systems/`, register one API with `window.toolrxSystems`, and carry their own
deterministic generator, so the same project seed produces the same bytes.
They add real behaviour — item counts, dialogue turns, combat damage, a
save/load round trip, quest progress, crafting costs, DOM panels, audio cues,
a weather cycle, a particle pool, and a small state machine — not placeholder
comments. One prompt can install several at once:
`add inventory and dialogue and save systems` creates three files, appends
their script tags before `app.js`, updates the README and ARCHITECTURE rows,
and records one undo entry. Repeating the same bundle reports
`already grown` and rewrites nothing; a partially overlapping bundle adds only
the missing systems. The preview inlines every system, so it still runs from
`file://`, and the whole set stays inside the 32-file and 512 KB caps. The
catalog reached 12,522 patterns here; step 41 trims the dead ones to 11,248,
and steps 43–44 add 86 more (bundles and extractors).

Step 41 is a quality pass on that catalog rather than a growth pass. The
generator now refuses to ship a pure literal that an earlier command already
shadows, so `build a rpg game with crafting` resolves to the general variant
instead of one of 1,080 unreachable duplicates, and target-free text commands
(`reverse the lines`, `uppercase it`) are declared before the generic
`reverse {text}` shapes that used to swallow them. `what weekday is it` means
today, not the literal text "it", and `what is my current project` reads project
memory instead of the generic recall key. `python3 toolrx/coverage.py` prints a
deterministic report over `toolrx/coverage.json`: catalog count, pure literals,
duplicate ids and regexes, dead literals, and every fixture family split into
exact-command, router, chat fallback, and refusal lanes with confidence and
margin distributions. `--write` regenerates the checked-in report and `--check`
fails when it drifts. The report is the justification for every catalog change:
all six long-form families resolve with zero chat fallbacks, builds and growth
are 100% exact, and the smallest measured margin is 0.025 (the context plan),
above the step-34 floor of 0.019.
`tests/test_coverage.py` pins the report's reproducibility, lane arithmetic,
margin floors, dead-literal audit, and the prefix index that makes the audit
linear instead of a quadratic scan.

Step 42 makes a long run legible after the fact. `lastRun()` is now a versioned
record (`toolrx.lastRun.v1`, schema v2): the one-line chip keeps the prompt size,
steps, time, bytes, files, and undo depth, and the chip expands into a per-step
table with `via`, wall time, confidence, margin, output bytes, and the step text.
The record also carries the planned-versus-executed step count, failures, the
files the run actually touched (diffed against a workspace snapshot taken before
the prompt), bytes written versus bytes emitted, the confidence and margin
distribution (`min`, `p10`, median, `p90`, `max`) rather than one scalar, the
context store's stored bytes, and headroom for files, bytes, time, steps,
characters, and context. Scalar `confidence` and `margin` remain as the minimum
of their distribution so the old chip contract still holds. The detail view
renders from the stored record after a reload, and `reset` clears both the record

Step 43 makes a workspace portable. `export this project` writes a
`toolrx.project` v2 bundle: the real file map, the build spec and its seed, the
last plan with per-step status, the project's context entries, the numeric
envelope it was written under, and the operator settings. `export the

are refused, and the plan must fit the 40-step cap. A workspace import is
all-or-none: it snapshots the workspace, verifies the write survived storage,
and restores the previous projects, flat files, and context on any failure.
Files round-trip byte-exactly, the plan and context are stable, the active
project and settings are restored, and a single-project package carries its

Step 44 adds four deterministic extractors for long intermediates, alongside
`summarize`, `headings`, `outline`, `firstlines`, and `table`. `extract the
list` returns bullet, numbered, and checkbox items in source order; `extract
the key facts` takes the first sentence of each prose paragraph and skips
headings, lists, tables, and fenced code; `outline the code` lists
`function`/`class`/arrow/`def` declarations as they appear; and `diff a and b`
walks a line-level longest common subsequence and prints added, removed, and
unchanged counts plus the changed lines. Each accepts a literal, a file path,
or the previous step, so `extract the key facts from notes.md then extract the
list` chains without a model. Three caps join the envelope: `extractChars`
(8,000, the input an extractor will read), `extractItems` (200, the output
lines it will emit), and `diffLines` (400, per side of a diff). Truncation is
printed (`(input truncated at 8000 of N chars)`, `(showing first 200 of 250
list items)`), an over-long diff is refused by name, and empty or marker-free
input returns a plain sentence instead of an empty string. `tests/
fixtures/extractors.json` pins every output byte; `tests/test_extractors_js.py`
checks determinism, the caps, the refusals, and the two-step chain, while
`tests/test_commands.py` pins the routing and arguments.

applies a five-patch bundle in one step, reads the generated README,
ARCHITECTURE, and app.js through the step-44 extractors, expands the stored plan

The project is 54,823 bytes with 10 files and 8 steps of headroom; every step
matched an exact command, so confidence and margin stay null rather than
inventing a probability. The report normalizes `at` and `ms` so it is
byte-for-byte reproducible; `python3 toolrx/demo.py --check` fails on drift, and
`tests/test_demo.py` asserts the plan fits, every step succeeds, the

Step 46 makes the catalog speak everyday English. `toolrx/everyday.py` is one
checked-in table of 541 phrasings across ten families — builds, edits, growth,

generated with polite prefixes (`can you …`, `please …`, `could you …`) and

`build_commands.py` and `tests/fixtures/everyday.json`, so the catalog and the
fixture cannot drift. Every fixture case resolves to its own exact command with
exact arguments: zero chat/router fallbacks, zero shadowing by an earlier

The active project is editable from chat: `change the page title to …`,
`add a theme toggle`, `make this project light`, and
`add a footer note saying …` rewrite the real `index.html` / `app.js` files.
The preview is re-bundled from those files, so a title, switch, or note
survives later theme changes and reopening the project. Project edits never
regenerate the page from its template.

Common game follow-ups are deterministic patches rather than new builds:
`add double jump`, `add three enemy types`, `add a boss`, `add a quest`,
`add day/night`, `add sound`, `make it harder`, `make the world 96x96`,
`switch to isometric`, and `make it 3d`. A patch updates the build spec, edits a
named function or constant in a real file (`doubleJump()`, `makeEnemy()`,
`spawnBoss()`, `questCheck()`, `SIZE`, the camera), appends an `## Applied edits`
block to `README.md` and `ARCHITECTURE.md`, and re-bundles the preview with the
list of changed files. `undo` restores the exact previous file map — including
removing `engine3d.js` after a 3D rebuild. Patches that do not fit the genre say
so plainly instead of changing something unrelated.

An optional LLM adapter exists for prompts the deterministic parser cannot
place. It is **off by default** and never runs as part of a normal build. You
configure an OpenAI-compatible endpoint, model, and key in Command Center →
LLM; the key stays in this browser's `localStorage` and is never logged, shown
in status, or written to the response cache. `llm status` reports the state,
`llm on` / `llm off` toggles it, and `llm cache clear` empties the cache. When
enabled, `llm plan a cozy mail route` only calls the model if the deterministic
parser returned `playground`; the answer must be strict JSON with an
allow-listed genre, and a miss falls back to an honest refusal. `llm patch
app.js with …` asks for a single unified diff, validates the file name and
every hunk against the current content, and stores it as a pending patch:
`apply the llm patch` writes it (and `undo` reverts it), while `discard the llm
patch` leaves the project untouched. Requests are HTTPS-only except for
localhost, with a call budget, timeout, response-size cap, and a 50-entry cache
keyed by the normalized prompt and file hash.

Builds cover calculators, notes, dashboards, landing pages, a social feed,
blog, forum, chat, arcade games (snake, breakout, pong, 2048, minesweeper,
tetris, maze, platformer, typing), the sixteen step-18 2D and 3D starters, and
a full seeded RPG. `plan a tower defense` or `blueprint an rpg` returns the
architecture instead of the finished page: state, modules, data flow, file
list, and build order.

The same command library also answers conversationally in a practical assistant
voice (`hi`, `remember my name is …`, `tell me a joke`). Emotional language is
met with care, but ordinary chat is not treated as therapy. Conversation memory
is explicit and inspectable: `remember my favorite color is teal`,
`make a note that …`, `what is my favorite color`, `what do you remember`,
`forget my favorite color`, and `forget everything`. Facts, notes, your name,
and the last build live under `localStorage`; nothing is inferred or sent
anywhere, and `what did i build last` reports the most recent project. It pulls
CORS-safe web data into `prev`:
`wikipedia ada lovelace`, `define serendipity`, `weather in reykjavik`,
`duckduckgo …`, then `summarize it` or `build a page about it`. A page build
writes a real research project under `projects/<slug>/` with the title,
paragraphs, and source link; `build a page about ada lovelace` performs the
lookup and the build in one step. Results show their source URL; failures are
reported honestly rather than invented.

The personal C++ and game-development archive is treated as a second library
that the command router can search: one metadata record per book (topics,
programming language, natural language, level, rights, source hash, reading
links), with the PDFs kept private and out of git. The same layer learns to
recognize programming languages in pasted snippets (C++, C#, C, Rust, Python,
JS/TS, Lua, shaders) and natural languages in prompts (Spanish, French, German,
Hindi, Japanese, and more), so `find a book about shaders`,
`list books by language c++`, and `what language is this: …` become ordinary
commands. Localized prompts are normalized to canonical English intents and
say so: `interpreted as: build a shooter game`. Spanish, French, German, Hindi,
and Japanese each cover fifteen common intents (builds, conversions, help,
archive search, language detection, jokes, and names), and `reply in Spanish`
switches the chat shell's own short messages with the preference saved in the
browser; missing packs fall back to English. The catalog, acquisition gaps,
schema, offline constraints, and phased acceptance tests are in
`toolrx/vision/LIBRARY-EXPANSION.md`; roadmap steps 21–25 track the build-out,
with 21–24 (catalog, language recognition, archive search, localized replies)
landed. The dashboard **Library** panel (▥) reads that same embedded catalog
offline: search, level/language/status filters, a next-up strip, and reading
status that is saved in the browser without touching the catalog file.

The Pages build is installable and works offline after the first visit: the
dashboard links `manifest.webmanifest`, and `sw.js` caches the shell, model,
command library, and templates. Navigation is network-first so a deploy is
picked up while online; assets fall back to the cache with a background refresh.
Bump `CACHE` in `toolrx/web/sw.js` whenever the cached asset list changes.

The ▤ button in the composer opens a searchable catalog of every generated
command, filterable by category. Selecting a row puts the pattern in the
composer and selects its first `{placeholder}`. Dialogs are keyboard-friendly:
`Escape` closes, `Tab` stays inside the active dialog, focus returns to the
opener, and `prefers-reduced-motion` disables the transitions.

Rebuild the library and the Pages copy after editing the dashboard, patterns,
router, or model:

```bash
python3 toolrx/build_commands.py
```

On phones (≤900px) the device drawer becomes a slide-over with a backdrop, the
device detail and command center become full-screen sheets, panes stack, the
preview opens as a full-screen sheet from the ▣ preview button, and the
composer uses a 16px field plus `100dvh` so iOS does not zoom or push it off
screen.

Mock fleet for screenshots (also demonstrates the context bar):

```bash
TOOLRX_MOCK=1 PORT=8080 python3 toolrx/server.py
```

The dashboard's device drawer opens via the ◈ button, or directly with
`http://localhost:8080/?drawer=open`. The mascot lives at the top of that
drawer and reacts when a device becomes active. The command center (mascot,
or `?cmd=open`) lists the local models it finds and holds the WireGuard
kill-switch; only the machine running the server is shown unless you add or
attach more devices.

## Configuration

| Variable | Default | Meaning |
|----------|---------|---------|
| `PORT` | `8080` | HTTP port |
| `TOOLRX_BIND` | `127.0.0.1` | bind address |
| `TOOLRX_SANDBOX_ROOT` | `policy.json` / package dir | root for file tools |
| `TOOLRX_RUN_DIR` | `toolrx/run` | gate/task state |
| `PREVIEW_DIR` | `preview` | generated preview artifacts |
| `TOOLRX_DEVICES_FILE` | `toolrx/devices.json` | optional local device inventory |
| `TOOLRX_SHOW_TRAINING` | off | show the optional phone-training UI |
| `TRAIN_SERIAL` | unset | adb serial for the optional training harness |
| `TRAIN_ANDROID_ROOT` | Android shared storage | shared-storage root on the training phone |
| `TOOLRX_LOCAL_BACKENDS` | Ollama + common local ports | comma-separated URLs probed for models |
| `TOOLRX_NEEDLE_DIR` | `../needle-agent` | optional needle/llama.cpp checkout |
| `TOOLRX_DISK_ROOT` | `/` | filesystem reported on the host card |

`devices.json`, `devnames.json` and `tasks.json` are local state and are
gitignored. Copy `toolrx/devices.example.json` if you want a persistent phone
fleet. Any adb-attached device is also discovered at runtime.

## Optional phone harness

The repo also contains the original distributed-phone experiment:
`adb-reconnect.py`, `forward-watchdog.py`, `hotplug.py`, `stack-watchdog.py`,
`job-scheduler.py`, and the gate/training scripts under `run/`. None of it is
needed for the router. To use it, copy `harness-devices.example.json` to
`harness-devices.json` (gitignored) and fill in your own serials; every serial
in the repository is an example placeholder.

Needle/llama.cpp backends are optional and off unless configured. The
deterministic router is the default and the only required path.

## Design notes

- **Default deny.** Queries are normalized, metacharacters are rejected, and
  file paths are canonicalized with `realpath` and confined to the sandbox.
- **No shell.** Tools call Python functions; `shell=True` is never used.
- **Bounded work.** Input length, file reads and output sizes are capped.
- **Deterministic.** The same query and model always produce the same route.
- **Honest benchmarks.** `bench/router_bench.py` reports feature throughput,
  routing throughput and end-to-end latency separately, with the corpus hash,
  token definition and hardware recorded alongside the number.
